# Shopify 后台与前台实施要点

按实际界面识别控件，不使用固定像素、前一店铺 ID 或固定日期。Windows UI 操作先读取当前安装的 computer-use 技能；登录与安全/隐私操作限制按该技能和当前高优先级指令执行。

本参考中的“打开、编辑、保存、点击”是**自动模式**实际操作；手动模式只据此提供对应路径、采用值和用户检查步骤，不实际修改后台。手动整包交付见 [manual-delivery.md](manual-delivery.md)。执行模式、常规/精品标准、Shopify正文自动化开关和自动预计送达是四个不同概念。

## 识别目标与记录现状

AdsPower 编号用于识别浏览器环境。确认窗口对应的域名、Shopify 后台 `/store/…` 和当前发布主题；不能误开另一个店铺。只读取任务相关标签，避免把邮箱、账号、密钥等无关内容输出到日志。

记录页面标题/handle、菜单和页脚绑定，并读取相关现有正文。用户要求直接生成并替换时，不主动导出历史政策，不将备份下载作为编辑前置步骤；易于取得的旧正文可保留，否则利用 Shopify 已有政策历史记录作为恢复线索。最终新正文仍保存本地副本。现有模板文案需要与已确认经营资料核对，不能直接复制其中的旧品牌、占位地址、日期或默认履约时效。

新建或重写政策时，先按 [store-standards.md](store-standards.md) 记录常规/精品模式及采用的时间规则表，再写入。局部链接/品牌任务沿用现有模式与正文。盘点也应覆盖六项原生政策及仍可访问但未挂页脚的旧页，不能仅按菜单清单认定无冲突。

## 六项书面政策

1. Settings > Policies，逐项查看 Written policies。退货规则及取消规则与书面正文是不同设置，分别核对。
2. 对支持手动编辑的书面政策，若 Use automated policy 开启并阻止编辑，先切换至手动内容模式。不要因此关闭客户隐私的 Cookie、opt-out、数据共享或地区设置。受当前工具限制的控件交由用户处理，仅暂停依赖该操作的部分。
3. 明确当前是富文本视图还是 HTML 源码视图。HTML 应在源码视图写入，返回富文本查看格式；普通正文直接写入富文本。不能为了隐藏可见标签而删除实际正文结构。
4. 每项保存后确认成功，再重新查看内容。Sidekick 只能作为可选填写途径，不能以其“已完成”文字替代真实保存及前台验证；也不能强求其编辑当前不支持的政策。

正式政策 URL 通常为：

| 内容 | URL 路径 |
| --- | --- |
| 退货退款 | `/policies/refund-policy` |
| 隐私 | `/policies/privacy-policy` |
| 服务条款 | `/policies/terms-of-service` |
| 物流 | `/policies/shipping-policy` |
| 联系信息、法律声明 | 从当前后台/前台读取实际链接后记录 |

优先保留已有原生政策页面；主题弹窗中同名文案并不等于后台正式政策已更新。

## 退货与取消规则同步

Settings > Policies > Return and cancellation rules 与下面的书面政策是不同对象。按本次已确认规则核对取消、退货窗口、起算点、标签/运费及补货费，不因更新一篇正文就认定后台同步。

2026-11-03核对的[Shopify原生取消选项](https://help.shopify.com/en/manual/fulfillment/managing-orders/returns/return-rules)为：No cancellations、Until item is fulfilled、15 minutes、1 hour、24 hours，**没有2小时**。后续执行仍检查实际可选项，不能要求用户寻找不存在的值。本用户已选择后续默认15分钟；若当前已是15分钟，核对后保留即可。

参考站“优先2小时邮件申请”不能直接等同于原生自助取消的配置值。遇到不支持的目标值应明确区分渠道及差异，不静默选成1小时或24小时。客户账户自助提交还依赖相应自助功能；仅在本次范围内配置，不擅自开启账号、安全或隐私功能。规则变更适用于后续订单，不据新窗口剥夺先前订单的适用权利。

## 服务弹窗迁移为公开页面

- 盘点页脚中的每个链接：原生政策链接、已有 Pages、主题服务弹窗、隐私选择入口。仅迁移用户指定范围。
- Online Store > Pages（有的版本入口可能变化），先搜索已有页面，避免重复创建。新建时填写标题与已确认正文，选择正确模板，设为 Visible，查看 URL handle 后保存。
- Contact Us 优先绑定现有含表单的 Contact 页面。部分自定义模板只显示主题 Contact form 的 Introduction，不读取 Pages 正文；遇到页面仍只有通用介绍时，在实际使用的模板介绍中补齐真实经营者、邮箱、电话及联系地址，保留原表单，不发送测试消息。
- 可采用清晰的 slug，如 `/pages/about-us`、`/pages/payment-terms`、`/pages/tools-product-guide`、`/pages/order-tracking`、`/pages/after-sales-support`、`/pages/terms-of-sale`。品类指南的名称与后缀取决于当前品类，宠物店示例不能套给日用品店。修改已有旧品类页面时同步正文、标题、SEO 与 handle，核对需要的旧地址重定向，避免重复创建；实际以保存后 URL 为准。
- Your Privacy Choices 必须实际点击检查：主题中同名区块也可能只是 `#InformationContent-…` 说明弹窗，不能跳过。先搜索已有 Pages，并核对实际 slug；有可用的 Shopify 原生 `/pages/data-sharing-opt-out` 时优先绑定它，不再创建同名说明页。资源选择器可能出现同名页面，选择后必须从前台确认实际 URL 与正文。
- 隐私选择的页面导航与实际同意/退出机制分开处理；保留真实机制，不以普通说明页替代可用的退出功能，也不借此更改客户隐私设置。

## 页脚绑定

1. 打开当前主题的 Customize/编辑器，找到 Footer 和实际对应的服务/政策区块。
2. 某些自定义主题在每个 Policy document 区块提供 **Optional published page override**：为服务区块选择刚创建的页面，保存后才算完成绑定。不是所有主题都存在此字段。
3. 对正式政策，保留正确的 **Use published store policy when available** 来源。该开关开启并不证明所有类型都能链接到原生政策；某些旧主题的 Contact Information、Legal Notice 仍会打开备用弹窗。先实际点击核实，优先用已有原生 URL/菜单配置修复；如现有主题只能通过 published page override 导航，可创建完整、公开且与正式政策一致的 Pages 副本并绑定，记录主正文来源，后续修订同步所有副本。没有此问题时不重复建页。
4. 无页面覆盖字段时，使用主题提供的链接设置或 Content > Menus 中的 Pages/Policies 资源链接。粘贴 URL 后，如界面要求下拉选择目标，完成实际选择再保存。
5. 没有配置入口且确需代码修改时，先备份相关主题文件，找到实际弹窗触发元素，最小改为真实页面链接并取消该入口的弹窗拦截。只处理已授权范围。
6. 保存当前主题，确认成功通知和保存按钮状态；切换前台后刷新。

逐项核对六项正式政策，不能仅因常见四项已显示就漏掉 **Contact Information、Legal Notice**；同时核对 **Your Privacy Choices**，原生页存在不等于页脚已挂。全部服务入口实际导航，标题与正文对应，例如实际是测量指南时使用Size Guide而非无数值图表的Size Chart。Content > Menus只适用于主题实际引用的菜单，自定义Footer资源字段可能独立于菜单，不能改了无效菜单就报完成。

### 页脚去重（用户要求时）

检查同一内容是否同时出现为独立链接、联系表单和折叠说明。已有正确的 Contact Us 与品类指南页面时，可通过 Footer 的 **Show contact form**、**Show pet/everyday tools sizing & care** 等显示开关关闭重复折叠区；名称以当前主题为准。保留地址、独立页面链接、六项政策和有效隐私选择入口，不删除底层 Pages 或整个 Footer。保存后刷新实际前台，确认重复区消失且其他入口仍可用。

### 页脚品牌末尾多余句点

页脚品牌与用户确认的展示名逐字核对，例如确认的是 `Vomdtjos`、`Phimhubx`，就不能显示成 `Vomdtjos.`、`Phimhubx.`。保留品牌本身确有的合法标点，不对店名、域名或全站文案做全局删点。

先判断字符来源：Footer 的可编辑品牌字段、Liquid 硬编码、或品牌元素的 CSS `::before` / `::after`。后台店名正确仍可能被模板追加句点；不要为消除模板装饰而改真实店名、域名或法定主体。

这类自定义主题的已观察实现位于 `sections/footer.liquid`，在 `footer-brand` 链接内：

```liquid
{{ shop.name | escape }}<span aria-hidden="true">.</span>
```

用户要求清除多余句点时，保留名称输出，只删除紧随其后的该装饰节点，改为：

```liquid
{{ shop.name | escape }}
```

手动位置：Shopify 后台 → Online Store / 在线商店 → Themes / 主题 → 当前主题的 `…` → Edit code / 编辑代码 → `sections/footer.liquid`；搜索 `footer-brand`，核对实际片段后再改。若实际实现不同，定位字符来源再给出对应修改，不把示例当作已核实的线上代码。

自动实施时沿用主题代码的最小可恢复修改要求，且只处理当前品牌旁的多余节点；不能批量删除其他 `span`、导航符号或 CSS，也不顺带装修主题。用户明确要自己修改时，只交付位置及前后片段，不保存线上变更。完成线上修复后刷新实际前台页脚，核对名称无额外符号、品牌链接及布局正常；未实际验证则记录为待用户修改/验证，不宣称已上线修复。

## 促销横幅与实际折扣（仅在授权范围内）

- 先看现售价、对比价、已有自动折扣/折扣码及用户最新要求。只要求修改横幅时不再新增减价；要求实际全店优惠时才实施活动。商品已降价后再建自动折扣，会按当前适用售价继续减免，不能把两种机制混淆。
- 七折 = 支付适用基价的 70% = **30% OFF**。读清用户指定的基价；不能用虚构对比价制造折扣。跨店逐店核对，不复制另一店的折扣对象、配置或状态。
- 可使用 Shopify 原生自动百分比折扣落实全店活动，核对所有顾客、适用商品/订单范围、最低门槛、组合规则、时区及生效时间。只填写已授权的条件，不默认增加期限、折扣码、最低消费或叠加优惠。保存后记录活动 ID 与激活状态；重入任务先查已创建对象，避免重复创建。
- 在当前发布主题的 Announcement bar 更新正文，明确自动应用、折扣码或门槛等实际条件。例如已配置自动全店减免 30% 时可写 `30% OFF SITEWIDE — Automatically applied at checkout`。没有实际活动时不能仅靠横幅声称优惠已经生效；不添加虚假倒计时、库存或原价声明。
- 在实际前台刷新检查横幅。先确认购物车现状，使用最少测试商品核对活动名称、折扣金额与小计，允许平台按货币最小单位处理舍入；不要凭自己算出的舍入方式改写结果。继续核对结账入口能进入真实结账，不能只看后台“已激活”或购物车数字。保留顾客原有购物车内容，不提交订单、付款或联系表单；恢复本次测试状态时遵守当前工具的操作规则。
- 遇到 `This cart uses a discount that needs a store review before checkout`，先定位主题及外部结账脚本，不能直接认定是 Shopify 风控或主题本身。某些第三方路由拒绝订单级折扣；改为商品级折扣仅是候选兼容方案，仍须验证真实结账。跨店承接时，A 店自动优惠不会因转移商品规格和数量而自动复制到 B 店；应核实实际承接店的优惠、币种及逐行金额一致，不能仅让前端校验通过。
- 若商品级优惠需通过系列覆盖全店，使用覆盖当前及新增适用商品的自动条件，并核对完整覆盖范围。仅供折扣筛选的内部系列应避免自动进入首页、分类和导航；创建前检查发布渠道，创建后实际复核。替换活动时先保存替代活动，再停用旧活动，确认无重复减免；不要删除旧记录或盲目修改商品原价。
- `cartState: unknown` 或长期 `pending` 是待核实的远端操作状态，不能承诺刷新或等待会恢复。保留原会话与请求证据，核查真实响应和服务端状态；不清空会话、不断创建新购物车或删除路由来绕过保护。确认状态与金额后才能恢复及验收。必要的已授权代码修复应有恢复副本，不关闭平台付款、安全或风控机制；尚未解决时明确报告结账阻塞。
- 复核 [Shopify 自动折扣说明](https://help.shopify.com/en/manual/discounts/discount-methods/automatic-discounts) 和 [Google 结账要求](https://support.google.com/merchants/answer/9158778?hl=en)。网站促销与 Merchant Center 的商品价格、促销提交是不同工作；不虚报已同步 feed 或已通过促销审核。

## 主题备用正文一致性

自定义主题的 **Bundled document content** 可能独立保留旧政策，甚至含 `#待填入`、旧经营者、错误时区或不同处理时效；仅更新 Settings > Policies 或 Page override 不会自动清除它。检查本次六项政策及相关服务区块的备用内容，将仍可能渲染的副本同步为同一最终正文并保存。联系方式、原运费、退货运费、退款各阶段和订单处理时间须与正式版本一致；不要把另一店铺的默认值复制进来。

## 联系资料覆盖与企业邮箱

将以下对象逐项单列核对，不能因其中一项正确就视为全站统一：General中本次涉及的公开资料、六项政策、相关服务页、**现有Contact表单模板的Introduction、Footer独立联系模块**、仍可能显示的备用正文及旧公开页。常见遗漏是原生Contact Information已有新地址/邮箱，但Contact页面和页脚仍保留旧地址、私人邮箱或MST/24小时回复承诺。

沿用用户已确认的真实主体及地址角色，不把某店个人资料固化为全技能默认。用户明确统一企业地址后采用其选择，无需重复审批；地址不能证明实际发货国家或仓库。

本用户偏好企业邮箱 `hello@实际店铺域名`，有授权时按当前域名采用，核对所有公开副本，不跨店复制旧邮箱。文案不能配置邮箱。只读DNS可记录当前查到的MX，但有MX不证明具体邮箱可收发，无MX也不足以独立断言邮箱不存在；分别报告证据与未验证状态。由用户实际发送、接收及回复测试，助手不擅自发消息、配置DNS或变更发信认证。

## 验证与恢复

从前台页脚逐一点击修改项，等页面加载完成，查看地址栏、标题、正文与返回行为。仅看到地址栏开始变化，正文仍是上一页时，需等加载后再次确认。原生政策、额外服务页、同名历史页面也需保持引用一致。

检查本次修改造成的空页、错误 handle、404、未公开、旧品牌、字面 HTML、遗漏链接绑定和弹窗仍被触发等问题。隐私选择页若按访问地区显示适用提示，记录实际所见及未执行退出提交；不能伪报退出控件可用，也不为验证而更改客户隐私设置。保留最终页面 URL 对照和已完成/未完成清单。

区分文案已生成、用户报告已保存、公开HTML已读取、真实交互已验证与待执行。手动不声称已替换上线；静态HTML不能证明真实点击、移动显示、隐私退出、邮箱收发、金额或结账已通过。未访问Merchant Center就将账号/商品源/配送及退货设置列为未核对，不把网站内容检查说成已获GMC批准。

Windows 控制工具报告实体 Esc 或用户停止时，当轮停止电脑操作并准确报告进度；后续用户明确继续时重新观察当前界面，不重复创建已保存页面。用户输入打断或页面状态变化后重新截图，不复用过期坐标。
